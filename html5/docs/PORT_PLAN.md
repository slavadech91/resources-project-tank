# План порта клиента Tanki 2014 в HTML5

Цель: браузерный клиент на Three.js + WebGL2 + TypeScript, который подключается к
существующему Python-серверу и использует оригинальные ассеты и физику.

Flash-версия (`dev/`, `src/`, `client/`) при этом остаётся рабочей и не изменяется.

## Принципы

1. **Физика — 1:1 из AS3**, без «улучшений» и сторонних движков (Rapier/cannon/ammo).
   Источник истины — наша боевая библиотека, читаемая копия в `decompiled/field_readable`.
   Порядок переноса и способ проверки — в `docs/HTML5_PHYSICS_PORT.md` корня проекта.
2. **Единицы и оси как в оригинале**: сантиметры, Z вверх. В Three.js переводим только
   в слое отрисовки (группа `world` с поворотом −90° по X). Логика и сеть — в оригинальных осях.
3. **Точность важнее красоты**: лайтмапы, те же текстуры, те же размеры. PBR/тени —
   только как опция, не по умолчанию.
4. **Проверка числом, а не на глаз**: эталонные трассы из Flash-клиента (позиция,
   ориентация, скорость, клавиши на каждом шаге) и сравнение с браузерной версией.
5. **Сервер не переделываем**: протокол реализуем на стороне клиента; браузерный TCP
   закрываем WebSocket-мостом.

## Этапы

### M0 — каркас и карта (сделано частично)

- [x] проект Vite + TypeScript + Three.js, камера, свет, сетка;
- [x] экспорт данных карты: `tools/export_map_data.py arena` → `html5/public/maps/arena/`;
- [x] разбор серверного `map_<map>.xml`: `collision-box`, `collision-plane`,
      `collision-triangle`, `spawn-point` — рисуем каркас карты;
- [x] разбор клиентского `map.xml`: расстановка пропов;
- [x] конвертер библиотек пропов `library.tara` → JSON-меши + текстуры
      (`tools/convert_proplibs.py <map|libs>`): 3ds парсится вручную (little-endian),
      текстуры копируются в `public/proplibs/<Lib>/tex/`;
- [x] настоящие меши пропов с текстурами в клиенте (пропы без модели — запасные боксы);
- [x] раскладка текстур как во Flash: видимые грани — по материалу 3ds, без переворота V
      (сверено скриншотами «Арены»);
- [x] освещение как во Flash (`src/map/lighting.ts` по `Lighting.as` и шейдеру Alternativa3D);
- [x] скайбокс карты (`src/map/skybox.ts`);
- [x] модели пропов в системе координат объекта 3ds (inverse матрицы 0x4160) — совпадают с коллизиями;
- [ ] туман (`fog_params`) и SSAO.

Проверка: `http://127.0.0.1:5180` — «Арена» с настоящими моделями пропов (мосты, стены, плиты).

### M1 — WebSocket-мост и логин (сделано)

- [x] сервис-мост `server/bridge.mjs`: принимает WebSocket, проксирует байты в 1212/1213
      (реализация RFC 6455 своя, без зависимостей; порт 5181, `/?port=1212`);
- [x] бинарный протокол в `src/net/`: `bytes.ts` (примитивы, `LenghtCodec`, optional map,
      нарезка пакетов, zlib через `DecompressionStream`), `codec.ts` (разбор по схеме);
- [x] схема всех моделей сгенерирована из серверного кода: `tools/gen_protocol_schema.py`
      (AST по `*_model_data.py` и `*_codecs.py`) → `src/net/schema-data.ts` — 68 моделей, 41 кодек;
- [x] логин: хэш-запрос → `SV_OPEN_SPACE` → канал пространства (хэш) → `SV_LOAD_DEPENDENCIES`
      → объекты (`LoadObjects`, команда 100000) → `300020048` (логин) → лобби;
- [x] разбор объектов всех пространств, в том числе боя: танки, карта, бонусы, статистика;
- [x] сервер: для клиента, который представился `client=html5`, SWF-ресурсы не отправляются
      (иначе логин занимал ~20 с из-за ожидания подтверждений загрузки ресурсов) — логин ~0.9 с;
- [x] команды моделей (сервер → клиент): схема из `*_model_commands.py` (91 команда),
      клиент отдаёт событие `command` с именем и аргументами; в бою ещё не проверено;
- [ ] команды клиент → сервер (движение, выстрел, вход в бой) из `*_command_handler.py`.

Проверка: `node html5/tools/ws-smoke.ts <логин> <пароль>` — в логе `[login-ok]` и данные
пользователя из `user_property_model`. В браузере — панель «Сервер» справа сверху.

## Что переносим 1:1, а что пишем заново

| 1:1 из оригинала | Пишем заново |
|---|---|
| Физика (подвеска, трение, столкновения, отдача) | Рендер (Three.js вместо Alternativa3D) |
| Протокол, model_id, форматы пакетов | Интерфейс (HTML/CSS вместо Flash UI) |
| Баланс, конфиги, карты | Загрузчик ресурсов (с конвертацией форматов) |
| Логика оружия и режимов | Эффекты (партиклы на WebGL) |

## Источники данных

| Что | Где |
|---|---|
| Коллизии, спавны, бонус-зоны | `dev/configs/maps/map_<map>.xml` |

| Серверные модели оружия | `src/scripts/global_models/battle/weapon/**` |

## Риски

- **Объём**: 929 классов в одной боевой библиотеке; работа идёт этапами, каждый этап проверяемый.
- **Восстановление имён полей** в физике — ручная работа (`docs/deobf/field_names.json`).
- **Формат `tara`/`3ds`** — нужны конвертеры, но формат простой и описан в `AGENTS.md`.
- **Основной клиент не декомпилирован** — интерфейс пишем заново по данным серверных моделей.

## Общий бой html5 + Flash (DM «Арена», Хантер + Смоки)

Разбор сервера (`src/scripts`): бой от типа клиента не зависит (`client_kind` влияет только на отправку SWF-ресурсов), сервер — ретранслятор плюс авторитет по здоровью/убийствам/бонусам. Значит основная работа в html5-клиенте; серверу нужны проверки и точечные правки.

Что клиент шлёт (`client/layouts/battle/models/*_command_handler.py`): `tank_model` — READY_TO_SPAWN 300100086, ACTIVATE 300100081, MOVE 300100084 (`int clientTime, short specId, MoveCommand`), MOVEMENT_CONTROL 300100085, ROTATE_TURRET 300100087, CONFIRM_SPAWN 300100082, DEATH_CONFIRMATION 300100083; `smoky_model` — FIRE 300100074 / FIRE_STATIC 300100075 / FIRE_TARGET 300100076; `battle_field_bonus_model` — ATTEMPT_TO_TAKE_BONUS 300100005; `inventory_item_model` — ACTIVATE 300100048; вход — FIGHT 300090007 (`battle_dm_info_model`) после открытия пространства `battle_select`. Сервер → клиент: PREPARE_TO_SPAWN/SPAWN/ACTIVATE_TANK/MOVE/ROTATE_TURRET/SET_HEALTH/KILL/SET_SPECIFICATION (`tank_model_commands.py`), shoot/shoot_static/shoot_target, fund_change, round_start/round_finish, spawn_bonuses/bonus_taken/remove_bonuses.

Этапы: 1) вход в бой и спавн (лобби → `battle_select` → FIGHT → пространство боя → READY_TO_SPAWN), отправка MOVE/ROTATE/CONTROL и отрисовка чужого танка; 2) выстрелы (fire*), эффекты чужих выстрелов; 3) урон, SET_HEALTH, смерть/респаун; 4) HUD: время (`time_left` + round_*), фонд, счёт и таблица убийств; 5) бонусы (ящики, подбор) и инвентарь; 6) выход из боя, раунды, переподключение.

Риски сервера: `maximum_allowed_tank_position_difference = 100` и позиция цели из клиента; `time_checker`/`latency` — заглушки; `shadow_map_correction_factor`, `incarnation_id`, `range` — подставлены наугад; `REFRESH_USERS_STAT` с тем же id, что `CHANGE_USER_STAT`; бой должен существовать в БД (создаёт Flash-игрок через лобби или запись в `battles`).

### Этап 1 выполнен (вход, спавн, движение, чужой танк)
Сервер менять не пришлось: он принимает и ретранслирует `MOVE` / `MOVEMENT_CONTROL` / `ROTATE_TURRET`, шлёт `SPAWN` / `ACTIVATE_TANK` (проверено двумя headless-игроками, `tools/battle-pair.ts`). Браузерный клиент: вход по кнопке «В бой», спавн в точке сервера, отправка движения по правилам Flash, чужой танк виден и едет (бот `tools/battle-bot.ts`). Не проверено с настоящим Flash-игроком — это следующий шаг. Известные упрощения: чужие танки без физики (экстраполяция по скорости), скин чужого танка всегда Хантер + Смоки, в `SPAWN` для DM приходит `team: 2`, спавн второго игрока на том же месте возможен (сервер выбирает точки), нет обработки смерти и выхода из боя.

### Этап 2 (выстрелы и урон) — код готов
`FIRE*` уходят на объект оружия, сервер наносит урон и шлёт остальным `SHOOT*` и `SET_HEALTH` (проверено `tools/battle-fire.ts`: здоровье 144 → 119). Автонаведение по вертикали портировано из `CommonTargetingSystem` (сектор ±0.9 рад, 412 лучей на сторону, выбор живого танка с наименьшим углом). Не проверено с Flash-игроком; нет смерти/респавна html5-танка (этап 3).
