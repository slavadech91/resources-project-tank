# Синхронизация v2 (html5, гибридная модель)

Решение пользователя (28.10): развиваем только html5, синхронизация переписывается с нуля «как в топовых играх»:
никаких рывков и телепортов, все попадания засчитываются, без невидимых танков. Модель — **гибрид**: свой танк
считает физику у себя (мгновенный отклик), сервер проверяет и ретранслирует, чужие танки рисуются интерполяцией
снапшотов, попадания проверяются с компенсацией лага. Старая синхронизация (Flash-подобная: MOVE по событиям,
50/50-смешивание физики чужого танка) сохранена в `backup/sync_v1/`.

## Почему было плохо (v1)
- Свой танк слал `MOVE` нерегулярно (смена управления, раз в 2 с, уход > 500 см) — у других игроков между командами
  чужой танк «угадывался» физикой, каждая команда дёргала его смешиванием 50/50 → рывки и телепорты.
- Нет общего времени: не известно, к какому моменту относится состояние; задержка и джиттер туннеля (TCP через
  WebSocket) напрямую видны как рывки.
- Сервер проверял попадание по последней известной позиции цели с допуском 15 м + скорость × возраст — либо
  отбрасывал честные попадания, либо пропускал всё.
- Существование танка у клиента держалось только на событиях SPAWN/KILL: пропущенное событие = невидимый танк.

## Схема v2

### Часы
`SYNC_PING` (клиент → сервер, на объект своего танка; первые 6 — через 150 мс, дальше раз в 1 с) / `SYNC_PONG`:
клиент оценивает `serverNow = performance.now() + offset` по замеру с наименьшим RTT из последних 16; смещение
подтягивается не быстрее 5 % хода часов (первый замер и расхождение > 1 с — сразу), чтобы время отрисовки не
прыгало. Серверное время — мс от старта процесса (i32). Первый PING регистрирует пространство клиента получателем
снапшотов боя (`src/tanks/net/sync/ServerClock.ts`).

### Свой танк → сервер
`SYNC_STATE` на объект своего танка **20 раз в секунду** по расписанию (и сразу при смене управления, не чаще раза
в 30 мс; без ограничения — перед каждым выстрелом и применением припаса): `seq`, `sample_time` (серверное время шага
физики, к которому относится `body.state`), `life` (spawn_token из `HEALTH_STATE`, пришедшего следом за SPAWN; пока
его нет — состояние не шлётся, через 500 мс клиент просит `HEALTH_SYNC`), управление шасси и башни, угол башни,
позиция, кватернион, линейная и угловая скорости. Старые `MOVE` / `MOVEMENT_CONTROL` / `ROTATE_TURRET` html5 больше
не шлёт. Фоновая вкладка: шаг боя и отправку держит воркер-тикер `main.ts` (~30 Гц).

### Сервер
- `sync_service.py`: приём `SYNC_STATE` → проверка (владелец, танк не DEAD / OUT_OF_GAME, `life == spawn_token`, `seq`
  новее последнего, путь по XY не длиннее `(макс. скорость × 2 + 1000 см/с) × dt + 300 см`, где dt — по времени
  приёма и снятия, не ниже `min_allowed_z`, не в килл-зоне, мины) → `tank_state` (как старый `move`) + история
  позиций (1.5 с) для компенсации лага. Нарушение скорости три раза подряд — `SYNC_CORRECTION` владельцу (последнее
  верное состояние). Обработчики обёрнуты в `guarded` (исключение не обрывает поток приёма), отправка в сокет — под
  `send_lock` (потоки снапшотов и приёма не перемешивают байты).
- Поток синхронизации боя, 20 Гц: `SYNC_SNAPSHOT` всем html5-клиентам боя — серверное время и последнее состояние
  каждого живого танка (`sample_time`, `seq`, `incarnation`, всё состояние).

### Чужие танки (клиент)
- `StateBuffer` на танк (`src/tanks/net/sync/StateBuffer.ts`): сэмплы по `sample_time` (повтор того же `seq` из
  следующего снапшота отбрасывается); время отрисовки `renderTime = serverNow − delay`.
- `InterpolationDelay` — одна задержка на бой (один `view_time` на выстрел): по каждому новому сэмплу «возраст»
  предыдущего последнего сэмпла танка к его приходу; цель — 95-й перцентиль за последние 120 сэмплов + 10 мс − 35 мс
  (последние 35 мс перед приходом можно экстраполировать почти без ошибки), 60…600 мс; к цели задержка идёт плавно
  (время отрисовки замедляется не больше чем на 10 %, ускоряется не больше чем на 5 %).
- Между сэмплами — кубический сплайн Эрмита по позициям и скоростям (если скорости согласуются с перемещением, иначе
  линейно; промежуток > 300 мс — линейно), slerp ориентации, угол башни — по кратчайшей дуге. За последним сэмплом —
  экстраполяция по скорости до 250 мс, дальше танк стоит (у танков старого протокола — до 2 с).
- `PoseCorrection`: показанная поза = буфер + поправка. В начале шага физики тело стоит в позе конца прошлого шага на
  то же время; если данные буфера изменились (новый сэмпл после экстраполяции, первый сэмпл после спавна, сдвиг
  задержки или часов), разница уходит в поправку, и она гаснет экспоненциально (τ = 65 мс, за 150 мс ~10 %). Скачок
  больше 10 м — перемещение (новая жизнь), без сглаживания.
- Тело чужого танка в физике кинематическое (`Body.kinematic`: для контактов — бесконечная масса, со статикой и с
  другими кинематическими не сталкивается, силы гусениц сбрасываются): перед шагом — поза на начало шага, после — на
  конец; отрисовка интерполирует между ними, столкновения и лучи оружия видят танк там, где он нарисован. Гусеницы и
  звук — по управлению из сэмпла. Труп после KILL — снова обычное тело (толчок, падение).
- Снапшот — источник истины о том, кто на поле: живой танк из снапшота, которого у клиента нет на поле (пропущен
  SPAWN, скрыт, вход в бой), появляется там, где он есть; пропавший из снапшотов на 2 с (при том что снапшоты идут) —
  убирается. Жизнь (`life`) отсекает прошлое: сэмплы старше известной жизни и жизни, в которой пришёл KILL, танк на
  поле не возвращают (при неизвестной жизни — 1,5 с после KILL); сэмпл новой жизни очищает буфер.
- Танк без снапшотов (клиент старого протокола) ведётся по его `MOVE`: сэмпл на время прихода минус половина RTT.

### Попадания
- Конверт выстрела v2 (`SHOT_ENVELOPE_V2`): как прежний (повторы, ACK, HEALTH_STATE), плюс `view_time` — серверное
  время, в котором стрелок видел цели (`renderTime` в момент выстрела).
- Сервер: позиция цели из истории на `view_time` (интерполяция), допуск 400 см + путь за 50 мс; отклонение по
  истории при совпадении со старой проверкой не отбрасывается (никогда не строже v1).

## Номера команд
| id | направление | что |
|---|---|---|
| 390000005 | к → с | SHOT_ENVELOPE_V2 (как 390000001 + i32 view_time в конце заголовка) |
| 390000020 | к → с | SYNC_PING: i32 ping_id, i32 client_ms |
| 390000021 | с → к | SYNC_PONG: i32 ping_id, i32 client_ms, i32 server_ms |
| 390000022 | к → с | SYNC_STATE (на объект своего танка) |
| 390000023 | с → к | SYNC_SNAPSHOT (на объект поля боя) |
| 390000024 | с → к | SYNC_CORRECTION (на объект своего танка) |

Состояние (в STATE, CORRECTION и в каждой записи SNAPSHOT), big-endian: `i16 seq` (16 бит по кругу), `i32 sample_time`,
`i32 life`, `i8 chassis`, `i8 turret_control`, `f32 turret_angle`, `f32×3 position`, `f32×4 orientation (x, y, z, w)`,
`f32×3 velocity`, `f32×3 angular_velocity` — 68 байт (`SyncProtocol.ts` ↔ `sync_service.encode_state/decode_state`).
SNAPSHOT: `i32 server_ms`, `i16 count`, затем `count × (i64 id объекта танка = user_id, состояние)`; приходит на
объект, на который шёл PING. Конверт v2: `i32 shot_id`, `i8 попытка`, `length count`, `count × (i64 цель, i32 жизнь)`,
`i32 view_time`, затем вложенная команда.

## Проверка
- `node html5/tools/sync-sim.ts` — офлайн: маршрут с разгонами, поворотами, резкими остановками и задним ходом,
  отправка 20 Гц по кадрам, снапшоты 50 мс, каналы с задержкой, джиттером и залипаниями TCP; наблюдатель — как
  `RemoteTank` (буфер + задержка + поправка вокруг шагов физики 33 мс). Результат (28.10): LAN — задержка 60 мс,
  ошибка 0; туннель 40±12 мс — 153 мс, ошибка p99 4 см; джиттер 80±45 мс — 345 мс, 4 см; залипания 400 мс (1 %) —
  491 мс, 7 см; телепортов 0 во всех сценариях.
- `html5/tools/sync-smoke.ts` — два клиента на живом сервере: A едет по кругу, B меряет ошибку и рывки по снапшотам.
